# ADR-012 — Embedding contract & widget library v1 (C12 / M16)

Status: Accepted
Date: 2026-08-15

Context:
Section 35 defines the embedding contract for vertical tools: islands via
`<div data-gw-app="name" data-gw-config='{...}'>`, mounted by
`gw.apps.mount()`; widgets are UI + configuration only (data via gw.db,
writes via operations/flows). Section 36 lists the reference verticals.

Decision:
- Embedding contract: `gw.apps.register(name, factory)` (idempotent —
  re-registering replaces the factory), `gw.apps.mount(root?)` (idempotent
  per island via a `data-gw-mounted` guard — re-running from data.html
  scripts on SPA route changes never double-mounts), `gw.apps.unmount(root?)`
  (runs the factory's optional cleanup and unmarks islands). Factories
  receive `{ el, config, gw }`; config comes from `data-gw-config` JSON —
  invalid JSON dispatches `gw:app-error` with a message; factory throws are
  caught and surfaced the same way. Unknown apps dispatch `gw:app-error`.
- SPA safety (the critical bug class of this step): the bootstrap script
  RE-RUNS on every SPA navigation (fresh SDK closures). Therefore the app
  registry and widget-load flags live on WINDOW
  (`window.__gwAppFactories`, `window.__gwWidgetsLoaded` /
  `__gwWidgetsLoading`), and the widget script has NO early-return guard —
  every execution re-registers into the shared registry (registration is
  idempotent). A per-closure registry caused stack overflows on the second
  navigation (lazy-loader recursion).
- Platform re-mount: ContentMount calls `window.gw.apps.mount(container)`
  AFTER html injection + script execution (inside the double-rAF run, before
  `gw:content-ready`). Content scripts may call mount themselves; the
  idempotent guard makes both safe and fixes the script-ordering race on
  SPA re-init.
- Widget library v1 (`lib/gw-sdk/widgets-source.ts`, served at
  `/gw-widgets.js`, lazily loaded by the SDK when a builtin island first
  mounts): menu, cart, checkout-flow, slot-picker, seat-map,
  account-dashboard, rewards, order-status, search-box. ALL config-driven:
  field names (titleField/priceField/bookedField/labelField/…) come from
  data-gw-config, never hardcoded. Data via gw.db/fetch of the generic APIs;
  writes via POST /api/cart (data-only cart) and gw.db.operation for
  booking ops; checkout-flow drives the C8 flow endpoints. User data is
  rendered with textContent only; config errors render inline messages.
- Widget loop closures use `let`/`const` per iteration (a `var` loop
  variable made every Add button target the LAST item).
- Demo: the fixture site gained a `/widgets` page embedding menu + cart +
  slot-picker, second menu object, slots objects (booked flag) and public
  type registrations for menu-items/slots (the data API requires
  registration or parentTenants).

Consequences:
- Widgets never re-fetch on the server; they are pure client islands.
- Trade-offs: checkout-flow's done-step detection matches a step id 'done'
  (convention documented in Section 31 examples); rewards reads the ledger
  via a config-driven customerId filter (anonymous users are prompted to
  sign in); seat-map reads ONE object with config-driven rows/seats paths.
- The window-level registry is shared across SDK closures — custom
  verticals' registrations survive SPA navigation by construction.
