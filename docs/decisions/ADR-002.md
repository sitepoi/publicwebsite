# ADR-002 — C2 tenant & site resolution, proxy convention, traffic rules

Status: Accepted

Date: 2026-08-15

## Context

Step C2 of the plan implements host → tenant resolution (relay-style),
Section 7.3 site resolution, traffic rules, and the middleware. Three points
needed implementation decisions: where the tenant registry lives, how Next.js
16 hosts the middleware, and how the relay route is guarded.

## Decision

1. **Tenant registry (Section 6):** one `settings` doc PER HOSTNAME (doc id =
   normalized host) whose data carries the tenant config — either a
   `tenantConfig` object (new) or a base64 `config` string (legacy relay/ras
   shape). `lib/resolver/tenant.ts` reads it through
   `DataProvider.getSettings([host])`. When the host has no registry entry,
   the resolver falls back to the deployment's DEFAULT tenant built from the
   Section 22 env contract (no hardcoded domains); unknown hosts then fail at
   site resolution with notFound (Section 7.3 rule 4). Firebase credentials
   resolve per-tenant env convention first, then the global
   `FIREBASE_ADMIN_CLIENT_EMAIL` / `FIREBASE_ADMIN_PRIVATE_KEY` env vars
   (single-tenant convenience).
2. **App registry (Section 7.1/Q12):** website-capable apps come from the
   `cms-settings` settings doc (`objectTypes[]` entries with `capabilities`
   including `'website'`). Fallback ("app fallback"): tenant's
   `defaultAppId` (new optional TenantConfig field), then the plan default
   `website-builder-uniconbaseapps` — never a hardcoded match.
3. **Wildcard matching (Section 7.3):** `*.domain` matches any host ending in
   `.domain` (one or more subdomain labels); the bare domain does NOT match.
4. **Middleware convention:** Next.js 16 deprecates `middleware.ts` in favor
   of `proxy.ts`. The plan's `middleware.ts` (Section 10) is implemented as
   `proxy.ts` with identical semantics (host normalization → `x-gw-host`,
   traffic rules). Same function, framework-renamed convention.
5. **Traffic rules (Section 19):** typed `TrafficRules` set in
   `lib/security/traffic.ts`; `DEFAULT_TRAFFIC_RULES` blocks nothing —
   deployments configure rules via the module API (or future env/config
   wiring). Middleware returns 403 on match, case-insensitive.
6. **Relay route guard:** `GET /api/relay/ras` requires the `x-relay-secret`
   header (RELAY_SECRET env, validated at boot). It returns a SAFE base64
   metadata subset (tenantId, databaseProvider, tableExtension, projectId,
   defaultAppId) — NEVER credentials (secrets env-only; clients couple to
   server routes per Section 6B).
7. **Caching:** per-host memory caches with short TTLs
   (`TENANT_CACHE_TTL_MS` / `SITE_CACHE_TTL_MS` = 60 s; negative results
   cached too). `invalidateTenant(host?)` / `invalidateSite(host?)` /
   `clearCaches()` are exported for the C11 publish-webhook purge work.

## Consequences

- No hardcoded domains or app ids; tenant isolation starts at host
  resolution.
- All data reads go through the DataProvider interface (Section 6B).
- The plan's route tree mentions `middleware.ts`; the repo uses `proxy.ts`
  (Next 16). Amend the plan if the middleware name must stay literal.
- Demo `FIREBASE_ADMIN_PRIVATE_KEY` in `.env.example` is a structurally valid
  throwaway key so boot works out of the box; real Firestore calls still
  fail with invalid-credential errors until real creds are set.
