1. The promise - what you get

The system answers one hard question: how does a team keep code, decisions and documentation from drifting apart, with an AI doing most of the work? It does that with one iron rule and one machine:

  • The iron rule: one HTML file per major feature = the single source of truth (SSOT) for every decision about that feature. No feature code change is pushed without the file being updated in the same change. A decision that is not written in section 11 of that file did not happen.
  • The machine: six Node scripts that scan those files, so documentation is not just prose - it is data. The scripts read the files to block bad pushes, stamp shipped tasks, generate changelogs, and build a control-tower index.

Concretely, once installed, you get:

Feature files (SSOT)npm run feature:new -- name groupTemplate + scaffolder script
Push gate on open risksautomatic in every releaserelease.js scans section 18 of every file

2. System overview in one page

The system has three layers:

  • Documents (in _docs/deny/_feature-development-management/): the feature files, the inventory, templates, shared css/js, satellites, and the generated index. Everything else in the system serves these documents.
  • Scripts (in scripts/, reachable through npm run): scaffolders, scanners, the release machine, and the changelog writer.
  • Rules (in .github/instructions/ + the copilot-instructions sync duty): text files the AI reads, so every code change made in chat triggers a document update in the same change.

5. The feature file - anatomy and contracts

A feature file is a normal HTML page with exactly 19 sections, plus a header, a meta table and KPI cards. It is both a document for humans and a data source for scripts. That dual nature is the heart of the system: the scripts do not need a database or a schema - the html attributes and table shapes ARE the schema.

5.0 The machine contracts scripts parse these

#ContractConsumed byViolation symptom
C1An <h1> must existcontrol tower indexFile silently missing from index.html (treated as an empty placeholder)
C2Meta rows Document version and Last updatedcontrol tower indexBlank version/updated columns
C3<span class="doc-status status-...">TEXT</span>control tower indexBlank status column
C4Section 11 rows: exactly 5 <td> cells, cell 1 = D-XXX-NN, cells 2 and 5 plain textauto-doc (parseDecisionRows)Decisions missing from changelog context
C5<section class="task-group" data-release-group="KEY"> and <div class="task-item" data-task-id data-group data-task-status>release.js stamper, control tower countsTasks not stamped on push; wrong counts
C6<div class="risk-item" data-risk-id data-risk-level data-risk-status> + .risk-solved-checkbox checkboxpush gate, control tower risk countsGate misses risks; wrong counts
C7<tbody id="release-log-rows"> containing the RELEASE-LOG-ROWS marker commentrelease.js release log writer"No SSOT document had a release-log marker - skipped"
C8Filename must NOT start with _all scannersFile completely ignored by the machine
Never rename the attribute names (data-release-group, data-risk-id, ...), the css class names (task-item, risk-item, risk-solved-checkbox), or the table cell shapes listed above. The scripts match them with regexes. "Improving" the html silently breaks the machine.

Every decision gets a row. The register is append-only: never delete rows - a reversed decision is marked Reversed (date) with a reason. The auto-doc parses rows with this exact regex shape, so keep the 5-cell structure and put plain text in cells 2 and 5:

5.5 Section 18 - risk register and the push gate C6

Every risk or side effect of a not-yet-pushed change is written here and linked to its release group. Before every push, re-evaluate every OPEN risk of the groups being pushed: solve it (tick the checkbox) or accept it (data-risk-status="accepted") with a reason and date.

      <p><strong>What can go wrong:</strong> [the side effect]</p>

      <p><strong>Mitigation:</strong> [what we do]</p>

LevelMeaningDefault gate behavior
criticalmandatory - blocks every push until solvedblocks
highblocks unless acceptedblocks
mediumwarnsreported only
lownice-to-havereported only

The gate logic (releaseContext.js): a risk is OPEN unless its checkbox is checked or its status is accepted/solved. The gate blocks when any open risk level is ≥ the threshold (default high, i.e. critical + high block).

Level calibration rule (user directive 2026-09-24): a risk level measures the production publish/usage impact of the code the risk describes - a documentation-only concern is never high/critical. Plan-stage risks for unbuilt code are recalibrated to their real production impact or accepted with the mitigation recorded in the Last re-evaluation line.

5.7 Two-state checkboxes - browser vs permanent

  • Browser layer: ticking a checkbox in the browser is remembered in localStorage per document (ssot-tasks:<file>, ssot-ideas:<file>, ssot-risks:<file>) - visible only in that browser.
  • File layer (permanent): data-task-status="done" on the task div, or checked="checked" on the checkbox - done for every browser. Written automatically by npm run rel for every stamped task, or by hand-editing the html.
  • Unticking a file-done task shows it as not-started in that browser only; on reload the file state returns.

6. The feature inventory (_features-list.html)

The roadmap and status board: one task per feature, grouped by domain, with priority chips. Rules of use:

  • Pick the next feature by priority: P0 first, then P1, then P2.
  • Set the feature's status chip to in-progress when work starts; tick its checkbox only when its SSOT file ships.
  • It lists the decision prefix reserved for every feature - check it before creating a file to avoid prefix collisions.
  • It records coverage: some features share one file, some are covered by an existing file. The inventory is the place where that mapping is visible.
  • It starts with _ so the scanners skip it - it is a working document, not a feature file.

7. The control tower index (index.html)

Generated by npm run ssot:index (also run automatically after each npm run rel). The builder walks the SSOT root recursively and, for every html file that has an <h1>, extracts:

ColumnHow it is computed
Featurethe <h1> text, linked to the file
Groupthe first folder of the relative path
Version / Updated / Statusmeta table rows (contracts C2, C3)
Decisionscount of <td>D-XXX-NN</td> rows
Groups / Taskscounts of data-release-group / data-task-id attributes
Open risksopen/total - same logic as the push gate
Releasesrows in the release-log tbody

Empty placeholder files (no <h1> yet) are skipped - so you can create placeholder files in advance without polluting the index. The index links the shared ssot.css / ssot.js so it looks like the rest of the system.

9. The six scripts

Full copyable code for all six lives in the kit under kit/scripts/. What each one does:

9.1 new-feature-doc.js - npm run feature:new

  • Copies _template/_ssot-template.html into <group>/<name>/<name>-ssot.html (without a group argument: <name>/<name>-ssot.html).
  • Replaces [FEATURE NAME] with the Title-Cased name, [CODE] with a suggested decision prefix (initials of the name words, max 4 letters), and the template date with today.
  • Rewrites ../ssot.css → ../../ssot.css and ../ssot.js → ../../ssot.js because the copied file sits one folder deeper.
  • Refuses to overwrite an existing file.

9.2 new-satellite-doc.js - npm run satellite:new

  • Usage: npm run satellite:new -- <name> <help|marketing|updates|social|onepager|presentation> [group] or npm run satellite:new -- monthly.
  • Fills [FEATURE NAME], [SSOT FILE] (relative link to the SSOT in the same folder), [DATE], [CSS_CLASS], and swaps [CSS_PATH]/[JS_PATH] per satellite type (onepager/presentation get their own shared assets).
  • Auto-detects the group by looking for <group>/<name>/<name>-ssot.html.

9.3 build-ssot-index.js - npm run ssot:index

  • Recursively walks the SSOT root, skips _-prefixed entries and index.html itself.
  • Skips files without <h1> (empty placeholders).
  • Extracts the fields described in section 7 and writes index.html.
  • Uses releaseContext.getOpenRisksFromSsotDocuments() for the risk columns, so the index always agrees with the gate.
  • Exported as a function too - release.js calls it after every release.

9.4 releaseContext.js - the shared brain (no npm script, used by others)

Exports helpers grouped in four areas:

  • a) Git context: getPushedCommit (git rev-parse @{push}), getLastPushTime, getUnpushedCommitLog, getCommitLogSince, getChangedFileList, getDiffSinceLastPush, getDiffSinceCommit (truncated in the middle to keep the AI prompt small).
  • b) SSOT decision registers: listSsotFeatureDocuments walks BOTH the SSOT root and a legacy _docs/deny/technical-decision-documents/ folder; parseDecisionRows applies the C4 regex; getDecisionRegisterContext returns only rows related to the current change - matched either by decision ID appearing in the diff/commits, or by being newly added to a document since the last push (found via git diff of the document).
  • c) Push gate: getOpenRisksFromSsotDocuments - the C6 logic; an open risk blocks according to its level.
  • d) AI chat history: scans VS Code Copilot transcripts (%APPDATA%/Code/User/workspaceStorage/*/GitHub.copilot-chat/transcripts/*.jsonl), scores them by how often the project path is mentioned, takes the best, filters messages by time, and truncates the tail. RELEASE_CONTEXT_FILE pins a specific transcript.

AI backend selection in getAiResponse, first available wins:

  1. The app's own AI gateway via UNICON_AI_GATEWAY_BASE_URL (+ optional key and chat-complete path), provider/model defaults deepseek/deepseek-v4-pro; the gateway is called with X-Unicon-Source: sitepoicms-automation.
  2. Any OpenAI-compatible endpoint via RELEASE_AI_BASE_URL + RELEASE_AI_API_KEY or DEEPSEEK_API_KEY.
  3. Local Ollama via OLLAMA_HOST + RELEASE_OLLAMA_MODEL.

It also loads .env.local then .env with dotenv (override:false - shell wins) so the gateway env vars work without exporting them; values are never printed.

9.5 release.js - npm run rel / npm run release

The one-command release. Exact sequence:

  1. git add -A. If nothing changed since the last push, only npm version patch + git push --follow-tags run.
  2. Push gate over every SSOT file (both folders, recursively). Blocking risks stop the release here.
  3. AI commit message: one line, max 72 chars, conventional-commit prefix, generated from changed files + truncated diff. RELEASE_COMMIT_MESSAGE="..." skips the AI.
  4. git commit → npm version patch → git push --follow-tags.
  5. Release log: a row appended to section 19 of every file with the marker.
  6. Stamp: with RELEASE_SSOT_GROUPS=all|key1,key2, every task in the shipped groups gets data-pushed-version/commit/at + data-task-status="done", groups move to pushed.
  7. Index: buildSsotIndex() is called.
  8. Doc commit: git add _docs/deny/_feature-development-management, commit "docs: update SSOT release logs", push - only if the doc updates actually changed something.

Sample gate output when risks block:

→ SSOT risk report - remaining open risks overall:
    high: 2
    medium: 1
→ Blocking risks for this push (level >= high):
    - html-tool-system-ssot.html: R-01 [high] An old tool relies on same-origin access
Release failed: Push blocked: 2 open risk(s) at or above the "high" level.
Review them with: npm run risks. Solve or accept them in their SSOT files,
then re-run - or run: npm run ship -- --force to ship anyway (gate warn mode).

Before you ship: run npm run risks for a clean, read-only report of every open risk (file, ID, level, title) and what blocks SHIP. npm run ship -- --force runs the full procedure with the gate in warn mode - risks are reported but no longer stop the push.

9.6 document-changes.js - npm run document:feature|month

  • Computes the range: since the last push (feature) or since the first commit of the current month (month).
  • Collects: code diff (middle-truncated), commit log, this project's chat transcript (tail-truncated), and related decision rows (from section 9.4).
  • Builds one big prompt with explicit rules: title # Changelog - <range>, sections Highlights / New Features / Improvements / Bug Fixes / Technical Notes, cite decision IDs only when actually related, end with Sources. Plain Markdown, no HTML.
  • Writes _docs/releases/<name>.md (override with RELEASE_DOC_OUTPUT).

A project-level rule that makes the AI update documentation automatically. Its essential text:

14. Installing into another project

The full checklist is in kit/INSTALL.md. In short:

  1. Docs root: create _docs/deny/_feature-development-management/ with _template/_ssot-template.html (from the kit). Copy ssot.css + ssot.js from the source project for the full visual experience.
  2. Scripts: copy the six files from kit/scripts/ into the project's scripts/. They work unchanged with the same folder layout; otherwise change the SSOT_DIR constants marked "ADAPT FOR YOUR PROJECT".
  3. npm scripts: merge kit/package-json-scripts.json into package.json.
  4. AI backend: set the gateway env vars or RELEASE_AI_BASE_URL + key, or use Ollama.
  5. AI chat context: works as-is on Windows + VS Code; otherwise adapt listAllTranscriptFiles or set RELEASE_CONTEXT_FILE.
  6. AI rules: add the sync duty to the project's copilot-instructions.md (adapted table) and create one instruction md per feature.
  7. Smoke test: npm run feature:new -- example core → npm run ssot:index → npm run document:feature. Run npm run rel only when you want to actually push.
  8. Tell the target project's AI the day-to-day rules (the five rules in INSTALL.md step 8) - the system only enforces itself if the AI and the humans follow them.

17. Gotchas

  • Template name - _ssot-template.html: the feature template was renamed from _feature-template.html to _ssot-template.html (2026-09-24) so its name says "ssot". Every script and doc reference was updated in the same change. If you use an OLDER copy of this kit, make sure the script path and the template filename agree - both must use _ssot-template.html, otherwise npm run feature:new throws ENOENT.
  • Underscore prefix is a hard rule: anything starting with _ is invisible to the gate, the index and the auto-doc. A feature file named _my-feature.html will never be scanned, never gate, never be stamped.
  • The <h1> test: a file without an <h1> is treated as an empty placeholder and missing from the index - even if it has content.
  • Keep the decision row shape: the parser regex wants exactly 5 <td> cells, cell 1 matching D-[A-Z]+-\d+, plain text in cells 2 and 5. Adding a 6th column (e.g. "Author") silently drops rows from the changelog context.
  • Keep the marker comment: section 19's <!-- RELEASE-LOG-ROWS ... --> is the anchor for automatic rows. Editing it away disables release-log writing for that file ("No SSOT document had a release-log marker - skipped").
  • Risk "solved" detection is checkbox-based: the gate treats a risk as solved only when the html contains checked on the .risk-solved-checkbox input, or the status is accepted/solved. A browser-only tick does NOT satisfy the gate - permanent done must be written into the file.
  • Stamping needs RELEASE_SSOT_GROUPS: without it, npm run rel ships code but does not stamp tasks - the file then shows stale not-done tasks for shipped work.
  • git rev-parse @{push} is the range anchor: the first release in a brand-new repo (no push yet) makes "since last push" helpers return empty/fallback values. Push once first, or set RELEASE_COMMIT_MESSAGE and accept the fallback diff.
  • dotenv is optional: if it is not installed, env-file loading is skipped silently and only the shell environment is visible to the scripts.
  • The auto-doc is this-project-only: transcript selection scores chats by project-path mentions. In a fresh project with few chats it falls back to the newest transcript - check the printed "Conversation source" line and set RELEASE_CONTEXT_FILE if it picks the wrong project.
  • Relative css/js depth: feature files live one folder deeper than the templates, so their links are ../../ssot.css; the scaffolder rewrites ../ssot.css → ../../ssot.css. If you copy a file by hand, fix the depth or the design will not load.
  • Plan-stage risks still block: the gate does not distinguish risks for unbuilt code from shipped-code risks. Follow the level calibration rule (production publish/usage impact) and accept-with-mitigation for planned work instead of force-shipping.
  • Never inline styles in feature files: the shared design lives in ssot.css; inline styles drift and fight the shared theme. (The portable template's tiny fallback <style> is the one exception - delete it after copying the shared files.)

18. FAQ

Does the system need a database?

No. All state lives in the html files themselves and in git. The scripts read html attributes and table rows - nothing is stored elsewhere. (The only extra state is browser localStorage for per-user checkboxes.)

What happens if the code and the document diverge?

By rule, the document is the tiebreaker: update it first to capture the final decision, then change the code. The AI instructions (sync duty) enforce this during chat work, and npm run rel refuses pushes that leave high/critical risks open.

Can I skip the AI entirely?

Yes. RELEASE_COMMIT_MESSAGE="feat: ..." npm run rel skips the AI for the commit message; document:feature is optional; the gate, stamping and index are pure code.

Why html files instead of markdown?

Because the documents double as data: attributes like data-task-id, classes like risk-item, and the table shapes give the scripts a parseable schema, while the shared css/js turn each file into an interactive workbench (task panel, tabs, KPIs, push-ready badges).

How do I know which prefix belongs to which feature?

The inventory lists the reserved prefix for every feature. Check it before creating a file. The scaffolder only suggests a prefix - uniqueness is your job.

One feature, one file - always?

Yes, with two documented exceptions both visible in the inventory: a feature covered by an existing file, and several small features sharing one file. The inventory is where the mapping lives.
