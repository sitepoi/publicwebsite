# ADR-013 — C13 final step: pilots, SEO routes, /app pages, template content fetch, fixture transactions

Status: Accepted
Date: 2026-08-17

Context:
The final build step (C13) requires two sample vertical pilots built ONLY
from CMS config + embedded data.html, the Section 2B parity sign-off
(CHECKLIST.md), the generator contract (rules-generators-v1.3.txt) and a
consolidated decision registry. Milestones M4, M8, M10, M15, M17, M18, M19
were open.

Decision:
1. Pilot A (restaurant) and Pilot B (bus tickets) are FIXTURE-DATA-ONLY
   (`lib/data/providers/fixtures/fixture-data.ts`): menu/categories objects,
   a create-order operation (transaction), a restaurant-checkout flow,
   trips objects with rows/seats, a ticket-checkout flow with the per-seat
   amount formula `seats.count * 25`, an issue-ticket operation, and the
   /restaurant, /tickets, /t/bus/<id> (M8 template content fetch) and /pnr
   pages. Verified end-to-end in `e2e/pilots.spec.ts` (payment mocked by the
   flow engine stub). No vertical logic lives in platform code.
2. Platform gaps found while building the pilots were closed GENERICALLY
   (not as vertical workarounds) and are logged in CHECKLIST.md:
   - Session-derived operation actors: flow/op routes now derive
     `{ id, roles }` from the HttpOnly session cookie
     (`resolveSessionActor` in `lib/auth`, roles from the users collection).
     Anonymous callers stay `roles: []` — this was a Section 32 bug, not a
     pilot feature.
   - The dev fixture provider implements `runTransaction` as an in-memory
     staging adapter (commit on success, discard on throw) so
     transaction-backed operations run in the emulator — dev-facility parity
     only, never a production path.
3. M4 SEO/discovery routes: `/sitemap.xml`, `/robots.txt`, `/llms.txt`
   (host-header driven, per-folder config; object types included via
   `webSettings.sitemapSettings.addObjectsToSitemap`) and an IndexNow ping
   (`lib/seo/indexnow.ts`) wired into `/api/revalidate` via the optional
   `indexNowUrls` body field — best effort, never fails the webhook.
   `feed.xml` remains a follow-up (CHECKLIST.md).
4. M10 capability pages: `/app/<appId>/...` resolves a page registered with
   slug `app-<appId>`; `PageKind` gains `app`, render-plan URL building and
   pathParams follow. Unregistered app ids are not-found.
5. M8 template content fetch: the resolver fetches the content object
   (type from the template page's `data.templateContentType`, fallback the
   template slug) and renders the CONTENT's own `data.html` when present,
   else the template page. Verified by the Pilot B trip page
   (`/t/bus/trip-101`) and unit tests.
6. Registry consolidation: CHECKLIST.md (Section 2B row-by-row ✅/🔶/❌),
   `docs/rules-generators-v1.3.txt` (every public capability), and
   `docs/migration-notes.md` (M11 runbook — documented, not executed: no
   legacy instance is attached to this repo). Changelog + plan version bump
   per Section 0C.

Consequences:
- Pilots are reproducible: start the dev server with `GW_DEV_FIXTURES=1`
  (default) and visit /restaurant, /tickets, /t/bus/trip-101, /pnr,
  /app/booking.
- The platform supports `/app` capability pages and content-driven template
  routes for all tenants, not just the pilots.
- Feed.xml and per-page chrome overrides stay open follow-ups (logged).
