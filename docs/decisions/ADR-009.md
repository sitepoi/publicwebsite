# ADR-009 — Auth sessions, first-party pages, gating & account scoping (C9 / M6)

Status: Accepted
Date: 2026-08-15

Context:
Section 17 replaces the legacy localStorage email+base64-password auth with
Firebase Auth + server session cookies; roles live in the users collection
(Uniconhub admin schema); pages gate via the `requireAuth` data field.
Section 32 requires user-scoped reads (`ownerField: customerId`) for account
data.

Decision:
- Session cookie: `gw-session` — HttpOnly, SameSite=Lax, Path=/,
  5-day Max-Age (Firebase max 14); `Secure` ONLY in production so dev/e2e
  over http://localhost keeps working (documented deviation from the plan's
  literal "Secure" — standard practice).
- Auth SERVICE abstraction (Section 6B): `lib/auth/types.ts` interface,
  Firebase adapter (`lib/auth/firebase.ts`), fixture adapter
  (`lib/auth/fixture.ts`), selected lazily by `getAuthService()` via dynamic
  import (keeps firebase-admin/auth — and its jwks-rsa/jose ESM chain — out
  of test/fixture module graphs). Passwords exist ONLY in the in-flight
  request: adapters never persist or log them; the fixture stores only
  SHA-256 digests (hard rule).
- Server-side register/login/reset/verify use the Firebase Identity Toolkit
  REST API (admin SDK cannot sign users in) with the optional
  `FIREBASE_API_KEY` env (absent → 503 auth-not-configured). Session cookies
  come from firebase-admin `createSessionCookie`/`verifySessionCookie`;
  logout revokes refresh tokens (best-effort) + clears the cookie.
- Roles: `users` collection doc keyed by uid, `roles: string[]` (Uniconhub
  admin schema). Register creates the doc (`['customer']`, name, createdAt);
  login ensures it when missing. Unknown roles default to `['customer']`.
- Endpoints: one route `/api/auth/session` (POST login/register/logout/
  forgot/reset/verify via strict discriminated union; GET = me) — guards:
  traffic rules, hashed-IP rate limit (10/60s, `auth:` prefix), honeypot,
  sanitized password-free error codes (email-exists 409,
  invalid-credentials 401, invalid-code 400, auth-not-configured 503).
- First-party pages `/p/user/[action]` (login, register, forgot-password,
  reset, verify): plain client forms posting to the session route; success
  navigates to `returnUrl` (only path-relative targets accepted — open
  redirects blocked). No localStorage password storage anywhere.
- Page gating (Section 17): server-aware — when the resolved page has
  `requireAuth` (true/'yes'/1) or is a private object
  (`rules.publicAccess === 'no'`), anonymous visitors redirect to
  `/p/user/login?returnUrl=…`; authenticated visitors render normally.
  Client gate: `gw.getUser()/isAuthenticated()` now real (boot-time
  `/api/auth/session` fetch, cached; `authReady` promise + `refreshAuth()`);
  `gw.login(returnUrl)`/`gw.logout()` drive the first-party pages.
- Accounts: `GET /api/account/[resource]` (profile, orders, tickets,
  bookings — strict whitelist). Collection reads use the NEW
  `DataProvider.queryRecords` and ALWAYS filter `customerId === uid`
  server-side (the client cannot widen scope — Section 32). Collection names
  follow `${resource}${tableExtension}` (C6/C7 convention).
- Fixture mode: fixture provider now supports in-memory record writes
  (createRecord/updateRecord/deleteRecord/queryRecords) and is a
  `globalThis`-keyed singleton; fixture auth the same. SINGLETONS MUST be
  `globalThis`-keyed: Turbopack dev emits multiple module instances
  (route handlers vs RSC pages), and `instanceof`/module-level vars do NOT
  share state across them.
- Route defaults: `providerFor` defaults now use the resolver stack's
  `getProvider` (fixture-aware) instead of raw `getProviderForTenant` —
  C7/C8 routes had the same latent bug (real Firestore in fixture mode).

Consequences:
- Supabase Auth can later replace Firebase behind the same interface.
- Trade-offs: `Secure` cookies off in dev (localhost); account reads return
  at most 100 records (v1); anonymous flows still rely on the opaque
  cookie + rate limit + honeypot (user sessions bind at C9+ via the users
  collection).
- Fixture provider is no longer strictly read-only for RECORDS (objects
  remain read-only); that only affects GW_DEV_FIXTURES environments.
