# ADR-010 — Payments, email, search & cart services (C10 / M9)

Status: Accepted
Date: 2026-08-15

Context:
Section 15 defines the service layer: Stripe PaymentIntents + webhooks,
AWS SES + nodemailer email, server fuse.js search, and (PART B) a server
cart feeding the C8 checkout flow. Hard rules: payment amounts are computed
server-side (never from the client), secrets are env-only, and the cart is
pure data.

Decision:
- Payments (`/api/pay/stripe/[fn]`):
  - `intent` accepts ONLY `{ flowStateId }` — the amount comes from the flow
    definition's payment step `amountFormula` evaluated over the server-side
    draft state (C8 computePaymentIntent); clients can never submit an
    amount (strict schema rejects extras). Currency likewise flows from the
    flow. The intent's metadata links `flowStateId`; a `payment-intents`
    record stores {amount, amountMinor, currency, status} for
    reconciliation.
  - `confirm` retrieves the intent server-side; on `succeeded` it updates
    order/invoice objects.
  - `webhook` verifies the Stripe signature (SDK constructEvent) and updates
    order/invoice objects on `payment_intent.succeeded`/`payment_failed`.
  - Object linking: order/invoice records carry `paymentIntentId` (written by
    flow operations via the `steps.payment.intentId` template); the webhook
    scans `orders{ext}` / `invoices{ext}` for that id and sets
    `paymentStatus` paid/failed. The client can never name records to update.
  - Stripe behind a `StripeService` abstraction (lib/pay) — official Stripe
    SDK; keys from the `<TENANT>_STRIPE_*` env convention (Section 22) with
    global STRIPE_SECRET / STRIPE_WEBHOOK_SECRET fallbacks; missing keys →
    503 stripe-not-configured.
- Email (`/api/email/send`): AWS SES + nodemailer (nodemailer composes the
  raw RFC-2822 message via stream transport; SES v3 delivers the buffer).
  Credentials env-only (SES_ACCESS_KEY_ID / SES_SECRET_ACCESS_KEY /
  SES_REGION / SES_FROM_ADDRESS). Template SELECTION is server-side: the
  client sends only `{to, templateId, subject?, data?}`; the template is an
  app object (`data.templateId`, html from `data.html` or
  `data.htmlPage.code.html`); `{{key}}` placeholders are merged with
  HTML-escaped user data (subject merged plain). Raw client HTML is never
  accepted.
- Search (`GET /api/search?type=&folder=&q=&lang=&limit=`): server fuse.js
  over PUBLIC objects — type access rules from the data API (publicAccess /
  parentTenants), private records excluded, `meta.language` filter, ranked
  by fuse, limited (max 100), memory-cached 60s per query. Optional
  Meilisearch later behind the same route.
- Cart (`/api/cart`): SERVER cart in a `carts{ext}` record per identity —
  anonymous clients get an httpOnly `gw-cart` cookie (30 days) with a random
  cartId; authenticated sessions use `user-<uid>`. Items CRUD via strict
  discriminated-union actions (add/update/remove/clear). Prices and totals
  are ALWAYS server-side (product price loaded from the stored object at
  add/update time; snapshots stored in the cart). Checkout goes through
  flows (C8) — the cart is pure data.
- Service abstractions (StripeService, MailService) follow the Section 6B
  pattern: adapters in lib/pay + lib/email, routes injectable for tests.

Consequences:
- Amounts can only change through flow configs — no client tampering.
- Trade-offs: webhook object updates scan only orders/invoices (extension
  agreed later); payment records link via paymentIntentId (flow operations
  must write it); carts are not merged between anon and user identities
  (future improvement); search is fuse over a 200-record window (v1).
