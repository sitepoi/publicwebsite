# Portable SSOT system - installation recipe for a NEW project

This kit gives any git + Node.js codebase the same
`_feature-development-management` capability as the source project:
one HTML file per major feature (single source of truth), an AI release
command with a push gate, auto-generated changelogs, and AI instructions
that keep md + SSOT in sync.

Read `_ssot-system-portable-guide.html` (next to this folder) for the
extremely detailed explanation of everything. This file is the checklist.

> Upgrading a project that already has an older kit? Read
> `kit/KIT-VERSION.md` (what changed) and paste `kit/UPDATE-PROMPT.md` into
> that project's AI chat. For one-command propagation from the source
> project, see `kit/SINGLE-SOURCE-SYNC.md` (`npm run kit:sync`).

---

## Step 0 - prerequisites

- git repo at the project root, with at least one pushed commit
  (the release flow compares against `@{push}`).
- Node.js 18+ (uses global `fetch`).
- `dotenv` in devDependencies if you want the scripts to auto-load
  `.env.local` / `.env` (`npm i -D dotenv`); the scripts still work without
  it - they just read the shell environment.

## Step 1 - create the documentation root

Copy this kit's folder layout into the target project root:

    <project>/
      _docs/deny/_feature-development-management/
        _template/
          _ssot-template.html           ← from kit/template/
        _portable-kit/                  ← optional: keep this kit for reference
        ssot.css                        ← copy from the SOURCE project (visual design)
        ssot.js                         ← copy from the SOURCE project (interactive behavior)
        index.html                      ← generated by npm run ssot:index - do not create by hand

The `ssot.css` and `ssot.js` live in the root of
`_docs/deny/_feature-development-management/` in the source project - copy
them verbatim. They are shared by every feature file. If you do not copy
them, feature files still render (the portable template has a fallback
style) but without the task panel, tabs and KPI counters.

Optionally also copy the satellite templates (`_help-template.html`,
`_marketing-template.html`, `_updates-template.html`, `_social-template.html`,
`_onepager-template.html`, `_presentation-template.html`,
`_monthly-template.html`) plus `onepager.css/js` and `presentation.css/js`
if you want satellite documents - see the guide, section "Satellites".

## Step 2 - install the scripts

Copy from `kit/scripts/` into the target project's `scripts/` folder:

    scripts/new-feature-doc.js
    scripts/new-satellite-doc.js
    scripts/build-ssot-index.js
    scripts/releaseContext.js
    scripts/release.js
    scripts/ssot-risks.js
    scripts/document-changes.js

They work unchanged if you keep the same folder layout. If you must move
the SSOT root, change the `SSOT_DIR` constant at the top of each script
(marked "ADAPT FOR YOUR PROJECT") - the constants in every script must
point at the same folder.

## Step 3 - add the npm scripts

Merge the entries from `kit/package-json-scripts.json` into the
`"scripts"` block of `package.json`:

    "release":          "node scripts/release.js",
    "rel":              "node scripts/release.js",
    "ship":             "node scripts/release.js",
    "SHIP":             "node scripts/release.js",
    "feature:new":      "node scripts/new-feature-doc.js",
    "satellite:new":    "node scripts/new-satellite-doc.js",
    "ssot:index":       "node scripts/build-ssot-index.js",
    "risks":            "node scripts/ssot-risks.js",
    "document:feature": "node scripts/document-changes.js feature",
    "document:month":   "node scripts/document-changes.js month"

## Step 4 - AI backend (required for rel and document:*)

The scripts need an AI to write commit messages and changelogs. Three
options, tried in this order (see releaseContext.js):

1. The project's own AI gateway: set `UNICON_AI_GATEWAY_BASE_URL` (and
   optionally `UNICON_AI_GATEWAY_API_KEY`, `UNICON_AI_GATEWAY_CHAT_COMPLETE_PATH`)
   in `.env.local` / `.env` or the shell. Rename these env vars in
   `releaseContext.js` if the target project's gateway uses different names.
2. Any OpenAI-compatible endpoint:
   `RELEASE_AI_BASE_URL=https://api.deepseek.com`,
   `RELEASE_AI_API_KEY=sk-...`, optional `RELEASE_AI_MODEL=deepseek-chat`.
3. Local Ollama: `OLLAMA_HOST=http://localhost:11434`,
   `RELEASE_OLLAMA_MODEL=deepseek-r1:14b`.

Without any of these, `npm run rel` falls back to Ollama on localhost.
`RELEASE_COMMIT_MESSAGE="..."` skips the AI entirely for the commit message.

## Step 5 - AI chat history (for the auto-doc)

`releaseContext.js` scans VS Code Copilot transcripts on Windows to add
"why" context to changelogs. It filters chats by project-path mentions and
works as-is for Windows + VS Code. For another OS/editor:
- rewrite `listAllTranscriptFiles` in `releaseContext.js`, or
- set `RELEASE_CONTEXT_FILE=/path/to/transcript.jsonl` to pin one file.

If no transcript is found, `document:feature` / `document:month` simply run
without chat context - everything else still works.

## Step 6 - wire the AI instructions (optional but recommended)

If the target project uses `.github/instructions/*.instructions.md` (VS Code
Copilot instruction files) or similar:
1. Add the "Documentation Sync Duty" section from
   `kit/copilot-instructions-sync-duty.md` to the project's
   `copilot-instructions.md` (or AGENTS.md), with the table adapted to the
   project's real features and unique D-prefixes.
2. Create one instruction md per feature from `kit/instruction-template.md`
   in `.github/instructions/`, pointing at the feature's SSOT file.

## Step 7 - smoke test (no database access needed)

    npm run feature:new -- example-feature core
    # creates _docs/deny/_feature-development-management/core/example-feature/example-feature-ssot.html
    npm run ssot:index
    # writes index.html - the control tower should list Example Feature
    npm run document:feature
    # AI changelog since the last push -> _docs/releases/feature-<date>.md
    # (fails gracefully without an AI backend / pushed commit)
    npm run ship
    # full release: gate -> commit -> version patch -> push -> stamp -> index
    # WARNING: pushes to git. Run only when you want to publish.
    # npm run risks            -> read-only report of open risks first
    # npm run ship -- --force  -> ship with the gate in warn mode

## Step 8 - day-to-day rules (tell these to the project's AI)

1. One feature file per major feature; never edit code of a documented
   feature without updating its file in the SAME change.
2. Every decision goes into section 11 with `D-<prefix>-NN`; the register
   is append-only.
3. Keep the 5-cell decision row shape, the task-group/task-item attributes
   and the release-log marker - the scripts parse them.
4. Files and folders starting with `_` are ignored by the gate, the index
   and the auto-doc. Feature files must not start with `_`.
5. Before every push, re-evaluate section 18 risks of the groups being
   pushed; `npm run rel` enforces this with the gate.
