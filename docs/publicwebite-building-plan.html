1. Purpose & Goals

  • Serve any number of websites from Uniconhub object management: each website = a folder inside a website-capable app.
  • Pages are objects; their data section (productData.data_categoriesBased) carries the generated HTML content — full native HTML/CSS/JS, no sandbox iframes.
  • One deployment serves all domains (like today), but with a clean pipeline and no legacy branches.
  • Dynamic pages on top of other CMSObjectTypes (products, events, articles) and capability pages (e.g. a restaurant ordering system rendered as a page section), supplied by first-party or third-party apps.
  • Gradual migration: legacy codebase keeps running old domains; new domains go straight to NEXT-GEN; content management is retired permanently after migration.
  • Application capabilities (Part B): the public layer is a generic get/set fabric between embedded tools and the CMS/Firestore — verticals (restaurant, tickets, e-commerce…) are separate tools/pages embedded like regular page content, and the platform provides query/operations/flows/permissions/ transactions/realtime so any complex scenario can be MANAGED properly.

3. Engineering Principles (no tech debt)

  • TypeScript strict everywhere — no any at boundaries; shared types generated/colocated with the data contracts.
  • One data source: Firestore objects via firebase-admin. The website layer never writes page content; writes happen only through Uniconhub tools or narrow, guarded APIs (forms).
  • Contracts first: every Firestore shape and every config shape has a Zod schema + version field (schemaVersion).
  • Server Components by default; 'use client' only for interactive islands (content mount, forms, SDK bridge).
  • Everything cached, cacheable, taggable — no per-request Firestore reads without a cache tier (memory → CDN).
  • Testable: the resolver/renderer are pure functions over (config, pageObject, request) → renderProps, unit-testable without Firestore.
  • Small surface: no framework re-implementations, minimal deps, pnpm, lint/format gates in CI.
  • Compatibility rule: Firestore collection names/suffixes and object schema MUST stay readable by Uniconhub admin — we never fork the data model.

Decision (2026-08-14): the platform MUST be able to switch database backends per tenant. v1 ships a Firestore adapter only; a Supabase adapter is designed-in and implemented later. Uniconhub admin keeps working on Firebase tenants; the provider choice is per-tenant config.

Yes — Firebase and Supabase specifics live in two fully separate adapters. They share only the common interface + the shared query/interpreter core. A per-tenant switch means changing tenant config; app logic and the other provider's adapter are never touched.

Rules that make the switch possible

  • Client never couples to a provider. All data access goes through server routes (/api/data/*, /api/forms, SSE for realtime) — the browser only talks HTTP to this app. Switching a tenant's backend touches zero generated content and zero client code.
  • Per-tenant provider config: databaseProvider: 'firestore' | 'supabase' in the tenant config + provider connection env per tenant.
  • Zod contracts (step C1) are provider-neutral; adapters map provider rows to the SAME shapes (object record, folder config, settings doc, SEO section).
  • Auth: session issuance abstracted too (Firebase Auth now, Supabase Auth later); roles stay in the users collection / mirror table.
  • Files: storage adapter (Firebase Storage now, Supabase Storage later).
  • Caching / tags / ISR stay provider-independent (Section 18).
  • Migration tooling (Uniconhub-side): export objects from Firestore → import into Supabase tables; the website layer needs no change beyond the tenant config.

11. Rendering Pipeline (RSC + content mount)

  • Page shell (doctype, head, chrome, footer) is React Server Components — never dangerouslySetInnerHTML on user data.
  • Page content is mounted by ONE client component (<ContentMount html=… css=… js=… pageId=… />): injects code.html, appends code.css to <head> (deduped), executes code.js after mount — typed, with a public lifecycle contract (events: gw:content-ready, re-init on route change).
  • code.js runs sequentially after double requestAnimationFrame inside an IIFE via Blob URL; top-level function declarations are hoisted to window; CMS-script errors are isolated from the app shell via targeted error capture.
  • Chrome is rendered from the reserved-slug site objects (default-header / default-footer / default-settings) the same way (ContentMount), cached per site (Section 7.4).
  • SEO head is assembled from the object SEO section + generated JSON-LD (WebPage/BlogPosting/FAQ/Product/Organization/Breadcrumb/Sitelinks) — pure functions, unit-tested.
  • v1 renders ONLY the page's data.html (the html-code equivalent). No block-type renderer is built — HTML/CSS/JSON content only for now; new content types can be added later if ever needed.
  • Traceability: the page container is auto-prepended with <!-- gw-page: <objectId> · slug: <slug> · updated: <ISO> · status: <status> --> (no secrets) — replaces the manual GW-PAGE-ID comment.

30. Object Operations & Server-side Business Logic

The CMS defines operations — the entire "set" side: payload schema, permission rule, validations, formulas, multi-doc writes and hooks. Vertical tools only send payloads; the platform enforces the contract. This is how complex scenarios are managed properly.

// operation definition object (in the website app, like form types)
{
  "operationId": "create-order",
  "writes": [
    { "targetType": "orders-uniconbaseapps", "mode": "create",
      "from": "payload", "with": { "customerId": "user.id", "status": "new" } },
    { "targetType": "products-uniconbaseapps", "mode": "update",
      "by": { "id": "payload.items[].id" }, "fields": { "stock": "decrement" } }
  ],
  "validation": zodJsonSchema,
  "permission": { "roles": ["customer"], "ownerField": "customerId" },
  "formulas": [ { "out": "total", "code": "sum(payload.items, price * qty)" } ],
  "hooks": [ { "type": "email" }, { "type": "contextFunction", "codeId": "notify-kitchen" } ],
  "transaction": true                    // all writes atomic
}
  • Server-side evaluation of context functions (Uniconhub user-defined JS) in a sandboxed, reviewed runtime — shared with the flow engine.
  • Operations are versioned; tools reference only the operation id.
  • Firestore writes stay admin-compatible (same collections and record shapes).

31. Declarative Business Flows (step-by-step processes)

Purchasing, booking, ticketing and registrations all follow steps → fields → validations → payment → hooks. That pattern becomes a flow definition stored in the app (like form types today), executed by the flow engine with server-side draft state. 

// flow definition object (in the website app)
{
  "flowId": "checkout",
  "steps": [
    { "id": "cart",      "dataDefinitions": [ /* items */ ],
      "validationRules": [ /* zod-ish rules */ ] },
    { "id": "delivery",  "dataDefinitions": [ /* address, time */ ] },
    { "id": "payment",   "paymentProvider": "stripe",
      "amountFormula": "cart.total + delivery.fee" },
    { "id": "done",      "hooks": [ /* create order object, email, decrement stock */ ] }
  ],
  "session": "cart"          // draft state key (anon token or user session)
}

// endpoints
POST /api/flow/{flowId}/start       → { flowStateId, step }
POST /api/flow/{flowId}/step        → { ok, nextStep } | { errors }
POST /api/flow/{flowId}/complete    → creates order/ticket objects + payment intent

Because flows are data, new verticals need only new flow configs — zero new server code. Complex requirements are expressed as data definitions, formulas, validations and hooks (Uniconhub already runs this model in dynamic forms — NEXT-GEN ports it cleanly to the server side).

32. Permissions & Data Scoping

  • Read: publicAccess on object types; private objects server-filtered; per-folder field allowlists.
  • Write: operations declare required roles (customer, agent…) and ownership scoping (ownerField: customerId) — users only touch their own orders, tickets and profile.
  • Anonymous operations (guest checkout, public forms) require captcha + rate limits + honeypot.
  • Tenant isolation comes from domain → tenant resolution (Section 6).

33. Transactions & Consistency

  • Operations marked transaction: true run as Firestore transactions: seat claim, stock decrement, order + payment record — all-or-nothing.
  • Idempotency keys (Idempotency-Key header / payload key) prevent double charges and duplicate orders on retries.
  • Flow draft state (Section 31) keeps multi-step scenarios consistent without holding long transactions.

34. Realtime & Events

  • gw.db.subscribe for live reads (order status, availability, dashboards).
  • Server events emitted by operations/hooks → outbound webhooks (kitchen, CRM, email) and an optional SSE/WebSocket channel for in-page live UI.
  • Event log objects keep an audit trail per tenant (admin-compatible).

35. Embedding Contract for Vertical Tools

Verticals (restaurant, tickets, e-commerce…) are separate tools/pages embedded like any regular page content — the platform never hardcodes them. What the platform guarantees for any tool:

  • Ship as a data.html page/section + optional JS app using gw.db / gw.forms / gw.db.operation / gw.db.subscribe.
  • data-gw-app="..." + gw.apps.mount() for reusable widgets (slot-pickers, seat maps, carts) that read field-group configs, not hardcoded fields.
  • Tools can register custom widgets: gw.apps.register('my-widget', factory).
  • Complex queries → Section 29 · writes → operations (Section 30) · processes → flows (Section 31) · permissions → Section 32. The tool is UI + configuration only.
