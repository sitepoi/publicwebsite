1. Purpose and governance

Onboarding a domain or subdomain onto this platform touches FIVE separate stores (DNS/hosting, the deployment env, the deployment's own Firestore registry, the tenant's Firestore config, the tenant's content). There was no single document listing all of them with field-level detail. This file is that single source of truth: every field, every location, every deterministic failure outcome, and the verification gate. The new tenant creation (the re-implementation of the legacy flow - the old project retires) MUST implement against sections 6, 8 and 10; any manual onboarding follows the same sections. When a requirement turns out to be wrong, this document is updated FIRST (section 12), then the fix is applied manually for existing tenants and/or in the registration module for new ones.

5. Verified problem and root cause

Onboarding a domain currently requires knowledge spread over the resolver code, five contract files, the env contract and the relay endpoint. Nothing enumerates the full set; a missed piece fails late and nondeterministically (a subdomain silently falls back to the default tenant, a missing credential fails at first render with a 500, a wrong hostNames list renders the wrong site).

Root cause: no single configuration contract document, and no writer-side validation - the registry is written by external tooling (legacy relay / sitepoi-relay) with only a Zod parse + console warn on this side.

6.1 L1 - DNS and hosting platform

  • REQUIRED DNS record (A/AAAA or CNAME) resolving the (sub)domain to the hosting platform.
  • REQUIRED The domain must be added to the hosting platform (e.g. Vercel project domains) so the platform terminates TLS and forwards the original Host header. The app matches sites by that Host header - a proxy that rewrites Host to the platform URL will always render the wrong site.
  • REQUIRED TLS certificate for the hostname (managed by the platform when the domain is added there).
  • OPTIONAL Wildcard DNS/platform domain if the site uses *.domain hostNames patterns (section 6.5).

6.2 L2 - Tenant registry entry (hostname → tenant)

Read by createRelayTenantLookup in app/lib/resolver/tenant.ts.

  • REQUIRED Registry today: the sitepoi-relay Firestore project, collection applications - one doc per application with hostNames[] + fbSettings.base64. The platform resolves the host against THIS store exactly like the legacy app does (server-side with firebase-admin credentials for the sitepoi-relay project). This store is not changed and no new registry format is required (D-DWH-10).
  • FUTURE OPTION A new-style registry doc in the DEFAULT tenant's Firestore, collection settings, doc id = normalized hostname. Normalization (normalizeHost): lowercase, strip trailing dot, strip numeric port, unwrap IPv6 brackets. NO protocol, NO path. www.acme.com:443 and WWW.ACME.COM both normalize to www.acme.com. Not required today - deferred to a later decision.
// FUTURE OPTION (not required today) - settings doc: id = "www.acme.com", in the DEFAULT tenant's `settings` collection
{
  "tenantConfig": {
    "schemaVersion": "1",
    "tenantId": "acme",                                  // REQUIRED, non-empty
    "databaseProvider": "firestore",                     // REQUIRED - 'firestore' implemented; 'supabase' throws designed-in
    "tableExtension": "",                                // OPTIONAL - table suffix for record collections
    "authTenant": "",                                    // REQUIRED - Firebase auth tenant used when creating users in the users collection
    "parentTenants": [],                                 // OPTIONAL - tenant ids whose types this tenant may also serve
    "firebase": {                                        // OPTIONAL block (firestore provider)
      "projectId": "acme-website-firebase",              // REQUIRED inside the block - the target tenant's project
      "clientEmailEnv": "acme_website_firebase_firebase_admin_client_email", // OPTIONAL - env var name override (prefix preserves case, section 6.3)
      "privateKeyEnv": "acme_website_firebase_firebase_admin_private_key"    // OPTIONAL - env var name override
    },
    "supabase": { "url": "", "serviceRoleKeyEnv": "" },  // OPTIONAL - only for databaseProvider 'supabase'
    "defaultAppId": "website-builder-uniconbaseapps"     // OPTIONAL - app fallback used when cms-settings has no website-capable app
  }
}

Fallback rule (must be understood): a host with NO valid registry entry resolves to the DEFAULT tenant from env (FIREBASE_PROJECT_ID). It then fails at SITE resolution with 404 UNLESS the default tenant's own site has a matching hostNames pattern (risk R-01). A registry entry therefore also serves to PIN a host to a tenant.

Legacy relay config mapping (compatibility): the legacy relay base64 (the sitepoi-relay applications docs, read server-side with firebase-admin - never through the unauthenticated old HTTP route) decodes to a Firebase client SDK config plus tenantId, authTenant and tableExtension. decodeRelayConfig maps it to tenantConfig BEFORE schema validation: projectId → firebase.projectId, tenantId → tenantId, tableExtension → tableExtension, databaseProvider = 'firestore', schemaVersion = '1', authTenant → authTenant (REQUIRED - user creation in the users collection depends on it). See section 6.11.

6.4 L4 - App registration in the target tenant (cms-settings)

Read by loadWebsiteAppDefinitions (app/lib/resolver/site.ts). Stored in the TARGET tenant's Firestore: collection settings{tableExtension}, queried by _id == 'cms-settings' plus tenantId filter. On existing tenants the doc id is cms-settings-{tenantId} with fields _id: 'cms-settings' and tenantId - a doc-id read (id = cms-settings) finds nothing. See section 6.11. 

// settings collection "settings{tableExtension}", _id = "cms-settings" (doc id "cms-settings-{tenantId}" on existing tenants), in the TARGET tenant's Firestore
{
  "objectTypes": [
    {
      "schemaVersion": "1",
      "id": "website-builder-uniconbaseapps",      // REQUIRED - the app id pages are stored under
      "capabilities": ["website"],                 // REQUIRED for site resolution - 'website' capability
      "rules": {
        "publicAccess": "yes"                      // OPTIONAL - gates CLIENT-facing /api/data/query + /api/data/{type}/{id} + search.
      },                                           //   'no' → 403 on those endpoints; type unregistered → 404 (unless parentTenants).
      "webSettings": {                             //   Page RENDERING (server-side) does not need this.
        "sitemapSettings": {
          "addObjectsToSitemap": "yes"             // OPTIONAL - include this app's objects in /sitemap.xml
        }
      }
    }
  ]
}
  • REQUIRED At least one objectTypes[] entry whose capabilities includes "website".
  • FALLBACK If no website-capable app exists, the resolver uses ONE app: id = tenantConfig.defaultAppId ?? website-builder-uniconbaseapps. A site can therefore exist without explicit registration - but register explicitly for clarity and for publicAccess/sitemap control.
  • LEGACY ENTRIES Existing tenants' objectTypes entries written by the legacy tenant creation flow (permissionSystem, permissionDetails, managers, editors, viewers, id, disabled, useFromRemote: 'yes') have NO capabilities, so those tenants always resolve through the FALLBACK app until capabilities are added. Add fields or add new entries - never delete legacy fields, never change the doc id. The entry id must equal the app id objects are stored under.
  • LEGACY CONTENT SYSTEM The old content system (sp_contents / sp_content_types, website-settings chrome) is NOT a render fallback in this platform - decided against on 2026-10-08, no sp_contents support (D-DWH-13). Old domains stay on the old application until their pages are re-authored as objects.
  • MULTI-SITE A tenant can host any number of websites. Each website = one folder inside ANY website-capable app instance (several instances of website-builder-uniconbaseapps with different ids and several third-party apps are all allowed). One folder can serve several domains via hostNames; one website can combine content from several apps through the data API across the registered apps. See D-DWH-14.
  • OPTIONAL rules.publicAccess: needed only if pages/widgets use gw.db.query, search, or detail endpoints for this app's types. Also used by page gating: a PAGE object whose own rules.publicAccess is 'no' (or data.requireAuth truthy) redirects anonymous visitors to /p/user/login.

6.5 L5 - Site folder and default-settings object

Read by createSiteResolver: scans each website-capable app for the object with slug default-settings; the FIRST one whose data.hostNames matches the host wins; its folder (record.typeId or record.id) IS the website root. Objects are read from om_objects{tableExtension} (or om_private_objects{tableExtension} when the app's rules.publicAccess is 'no'); folders are docs in om_object_types{tableExtension}. See section 6.11.

Host matching semantics (exact rules from hostMatches):

  • Exact match: acme.com matches only acme.com.
  • Wildcard: *.acme.com matches any host with AT LEAST ONE label before acme.com (www.acme.com, shop.acme.com). The BARE domain acme.com does NOT match *.acme.com - list both when needed.
  • First website-capable app with a matching default-settings object wins; scan page size is 200 objects per app.
  • No match → deterministic 404 (site-not-found), never a fallback to another tenant's content (but see F-02/F-03 for the fallback-to-DEFAULT-tenant path).

Legacy website-settings doc: the old application's website-settings-{tenantId} doc (_id: 'website-settings') is read only by the old application and is ignored by this platform; it must remain untouched.

6.9 L6 - Publish and cache invalidation

  • REQUIRED POST /api/revalidate with header x-revalidate-secret: REVALIDATE_SECRET after publishing content (else up to TTL latency). Body: { "tags": ["host-www.acme.com", "site-<folderId>"], "indexNowUrls": [...] }. The call purges Next cache tags, clears tenant/site resolver caches AND the app-store widget catalog cache.
  • Cache tags: site-<folderId>, page-<objectId>, type-<appId>, host-<host> (isPurgeableTag rejects other shapes).
  • TTLs without purge: tenant + site resolution 60 s; data query API 30 s (memory); app-store catalog 300 s.
  • Preview: ?gw-preview=<previewSecret> shows draft pages (status 'draft') - use for shadow review before go-live.
  • Unknown → the CMS publish path should call this endpoint (store-side webhook wiring for the widget catalog is still open in the appstore repo).
  • LEGACY CONTRACT: the old application's /api/revalidate expects body {secret, hostname, paths, contentId} and purges tags content-{contentId} / host-{host}. It keeps serving old domains unchanged. During cutover the CMS publish webhook must call the old endpoint for old domains and this endpoint for new domains.
  • WHY TWO CONTRACTS: the old contract sends the secret in the request body and purges by URL paths; the new contract sends the secret in a header and purges by typed tags (site / page / type / host), so ONE call clears every cache layer (Next tags + resolver memory caches + app-store catalog). The new contract is the better one; old domains keep the old one only until they migrate.
