# ADR-001 — C1 scaffold: app location, env contract, provider layering

Status: Accepted

Date: 2026-08-15

## Context

Step C1 of the GeneralWebsite NEXT-GEN plan (`docs/generalwebsite-nextgen-plan.html`)
scaffolds the clean-room Next.js codebase inside the existing repository and
builds the contract layer (M0 + M1). The repo root already contained non-app
files (`docs/`, `.git`), the env contract (Section 22) lists variables that
are only relevant for feature-gated capabilities, and the DataProvider
abstraction (Section 6B) requires Firebase/Supabase code to stay fully
separate.

## Decision

1. **App location (Section 27):** the Next.js app lives in the `app/`
   subfolder of the repo (`<repo>/app/`); App Router routes are at
   `<repo>/app/app/`. CI `defaults.run.working-directory: app`.
2. **Env contract (Section 22):** `lib/config/env.ts` Zod schema covers every
   variable listed in Section 22. Required at boot (fail fast via
   `instrumentation.ts`): `NODE_ENV`, `NEXT_PUBLIC_APP_NAME`,
   `FIREBASE_PROJECT_ID`, `FIREBASE_ADMIN_CLIENT_EMAIL`,
   `FIREBASE_ADMIN_PRIVATE_KEY`, `RELAY_SECRET`, `FORMS_RATE_LIMIT_MAX`,
   `FORMS_RATE_LIMIT_WINDOW_MS`, `REVALIDATE_SECRET`. Feature-gated optional
   (absent = feature disabled, because reCAPTCHA/SES/IndexNow/Sentry are
   per-tenant/per-folder config — Sections 14/15/16/20):
   `RECAPTCHA_SITE_KEY`, `RECAPTCHA_SECRET_KEY`, `SES_ACCESS_KEY_ID`,
   `SES_SECRET_ACCESS_KEY`, `SES_REGION`, `INDEXNOW_API_KEY`, `SENTRY_DSN`.
   CI copies `.env.example` → `.env.local` so the boot validation runs against
   the same contract in builds.
3. **Zod tolerance strategy:** parse-level schemas for Uniconhub-owned shapes
   (objects, folders, app config, SEO, operations, flows) use optional fields
   + `catchall` so real admin-authored records and the Section 7–8 JSON
   examples parse exactly; the platform-controlled request payload
   (`DataQueryRequestSchema`) is `.strict()`. Every shape carries an optional
   `schemaVersion` field (Section 3).
4. **Provider layering (Section 6B):** `lib/data/provider.ts` defines the
   `DataProvider` interface; `lib/data/common/` is the shared query/filter/
   facet/relation interpreter used by both adapters;
   `lib/data/providers/firestore/` and `lib/data/providers/supabase/` are
   fully separate (no cross-imports). `lib/firestore/admin-app.ts` builds
   firebase-admin apps from env-only credentials (Section 22 per-tenant
   convention) and is imported ONLY by the Firestore adapter. A Supabase
   tenant currently throws "designed-in, not implemented".
5. **Firestore adapter v1 baseline:** `contains` filters, `search` and
   `facets` are interpreted over the fetched result window via the common
   core; `total` is exact only for Firestore-translatable filters. Hardened
   with the data API in C7.
6. **Status semantics (Section 8/Q9):** `status` lives in the normalized data
   section; absent/empty = published.

## Consequences

- All app code builds against the interface; a per-tenant backend switch is a
  tenant-config change only.
- Env failures surface at boot/build, never mid-request.
- `app/app/` nesting is an accepted readability trade-off for following the
  Section 27 rule literally; revisit only via the change protocol (Section 0C).
