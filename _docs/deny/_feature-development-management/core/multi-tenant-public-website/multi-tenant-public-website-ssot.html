1. Purpose and governance

The publicwebsite application is a content AGGREGATOR and RENDERER. It does not own any content: it reads content from other tenants, applications and folders through a configured public read API, then renders the assembled pages for www.uniconhub.com. Tool/application data (web contents included) stays together in the applicationstore tenant, general (non-tool) website pages keep coming from the cms tenant, and the rendered site is served at www.uniconhub.com. This file is the single source of truth for every decision about that platform.

5. Verified problem and root cause

The platform today resolves ONE host → ONE tenant → ONE database provider → ONE site folder, with admin credentials to that tenant's own database (C-01..C-04). Every page of a site must live in that one folder. What is missing, per the accepted feature request of 2026-09-24:

  • assembling pages from MANY tenants, applications and folders over a public HTTP API - today there is no HTTP read path at all (verified: no publicApiBaseUrl, serviceToken, source registry or hooks/publish anywhere in app/);
  • config-only onboarding of new sources - today a new tenant needs tenant config + admin credentials + provider wiring;
  • collection renderer kinds (listing/category/detail) - only the client-side list widget exists (C-08);
  • a per-tenant public read API with per-source service tokens and the absolute om_private_objects guarantee;
  • cross-source slug resolution with registry-order priority and a tenant-prefixed fallback path for collisions;
  • a source management UI (add/edit/disable/remove, test connection, per-source health, cache clear).

Root cause: the resolver and render plan are scoped to a single resolved site folder (one provider, one object space). There is no source registry, no HTTP read adapter and no public API surface, so multi-source aggregation cannot be expressed in the current pipeline.

6. Requirements

  1. Aggregator, not owner: publicwebsite reads content from other tenants through a configured public read API and renders it; it never owns or copies the content (request §1).
  2. Content-source registry (config-driven): one entry per (tenant, mainObjectType, folder set); multiple entries per tenant allowed; entries may point at different tenants simultaneously. Adding a source is a configuration change, never a code change (request §3).
  3. Public read API per tenant: GET /objects (query: mainObjectType, repeatable typeId, status, q, sort, page, limit ≤ 200, fields projection; response: items/total/page/hasMore/cursor) and GET /objects/{id}. Serves om_objects ONLY; om_private_objects is never served - not in listings, not by id, not through any fallback or projection (request §4).
  4. Service tokens: per-tenant, viewer (read-only) scope. The token is an API key defined in the target tenant's CMS API key definitions; it may have expiry or no expiry, exactly as defined there (D-MTPW-09). CORS allows only the publicwebsite origin(s). Rate limiting and per-token request logging required (request §4).
  5. Routing and slug resolution: a URL resolves to one registered source and one object via the source's slugField; slug collisions resolve by registry order (priority); collection sources support category pages (/products/{category} → folder/typeId) (request §5).
  6. Rendering: fragment-page = platform shell + object body as fragment (one root div, scoped css, idempotent js, no html/head/body) + object SEO fields into the head; collection = listing (paginated cards), category (grouped by folder), detail (field layout per source mapping). Only objects with status matching the source filter (published) render; unpublished or missing slugs → 404 (request §6).
  7. Source management UI (admin-only): add/edit/disable/remove entries; test connection (run the configured query, show first results or the exact error); per-source health (last success, object count, error message); clear one source's cache. Changes take effect without redeploying (request §7).
  8. Caching: per-source TTL from the registry entry (default 300 s), cache keyed by source id + query params; optional publish webhook (POST /hooks/publish with object id) invalidates the affected source cache entries (request §8).
  9. What does not change: tool writes stay tenant-scoped; all tools/applications and their web contents stay together in the applicationstore tenant; cms keeps serving general pages as a configured source; om_private_objects stays private forever (request §9).
  10. Acceptance criteria (request §11): (AC1) an applicationstore page appears on www.uniconhub.com under its slug within cache TTL with no code deployment; (AC2) a cms page appears the same way - both tenants serve the same site at the same time; (AC3) a third tenant needs only a registry entry + service token; (AC4) an om_private_objects id returns 404 in every tenant, endpoint and projection; (AC5) a tenant's token cannot read any other tenant, and within its tenant follows the CMS API key definition (updated by D-MTPW-09); (AC6) disabling a source removes its pages immediately (404); (AC7) a slug collision resolves by registry order and the losing page stays reachable under its tenant-prefixed fallback path.

8. Solution design

The pipeline becomes: resolve host/site (existing C-01..C-03) → resolve the URL against the content-source registry (new) → read the object(s) from the source tenant over its public read API with the source service token (new HTTP adapter) → build the RenderPlan (fragment-page: existing; collection: new) → render the platform shell (existing). Registry entry schema (from the accepted request §3):

{
  "id": "tool-webpages",
  "label": "Tool webpages (applicationstore)",
  "enabled": true,
  "tenant": {
    "name": "applicationstore",
    "publicApiBaseUrl": "https://applicationstore.uniconhub.com/api/public",
    "auth": { "type": "serviceToken", "tokenId": "pw-read-appstore" }
  },
  "source": {
    "mainObjectType": "<website page type>",
    "folderIds": ["tool-pages-root"],
    "recursive": true,
    "filters": { "status": "published" }
  },
  "mapping": {
    "slugField": "slug",
    "statusField": "status",
    "titleField": "name",
    "bodyField": "webpageContentWithBuilder",
    "rendererKind": "fragment-page",
    "listTemplateId": "tool-page-list",
    "detailTemplateId": "fragment-shell"
  },
  "cache": { "ttlSeconds": 300 },
  "updatedAt": "2026-09-24"
}

Registry rules: one entry per (tenant, mainObjectType, folder set); multiple entries may point at the same tenant; entries may point at different tenants at the same time; the same renderer kinds apply everywhere. Auth is tenant-level: every source of a tenant uses that tenant's token; expiry or no expiry follows the API key definition in the target tenant's CMS (D-MTPW-09). Day-one registrations: tool pages from applicationstore (fragment-page), general website pages from cms (fragment-page), products and blog posts from applicationstore (collection, future).

Benefit: request §4 fulfilled for detail reads; AC4 covered for this endpoint.

Problem it solves: without token scoping the whole om_objects table is open to anyone with network access.

How we will solve it: per-tenant service tokens - one API key per consumed tenant, defined in the target tenant's CMS API key definitions (expiry or none per the definition), viewer scope (D-MTPW-09); CORS restricted to the publicwebsite origin(s) (www.uniconhub.com included).

Benefit: AC5 enforceable; least privilege per source.

Files: app/app/api/public/*, app/lib/security/

Problem it solves: public endpoints need abuse protection and an audit trail (request §4).

How we will solve it: reuse the existing rate limiter pattern (hashed-IP or per-token) and pino logging with token id + source id per request.

Benefit: abuse-resistant, auditable public API.

T-09 Security tests for the public API Mandatory

Problem it solves: AC4/AC5 are absolute security rules - they must be verified per endpoint and projection, not trusted.

How we will solve it: tests: om_private_objects id → 404 in listings, by id, under every projection and fallback; a tenant's token cannot read another tenant, and within its tenant follows the CMS key definition; CORS rejects other origins; rate limit returns 429.

Benefit: the security boundary is proven before anything public ships.

T-10 HTTP source read adapter Mandatory

Problem it solves: the pipeline has no way to read objects from another tenant over HTTP.

How we will solve it: a read adapter implementing the object-read contract over GET /objects + /objects/{id} using the source's publicApiBaseUrl + service token; maps the stable response shape onto ObjectRecord-like data for the render plan; per-source TTL cache keyed by source id + query params (D-MTPW-08).

Benefit: sources become first-class read paths in the existing pipeline.

Files: app/lib/data/providers/http/, app/lib/cache/

T-11 Multi-source slug resolution in the page pipeline Mandatory

Problem it solves: today a URL resolves against ONE site folder (C-04); it must resolve against all enabled sources in registry order.

How we will solve it: extend the resolver: for the resolved host, run slug lookup across enabled sources in priority order; first hit wins (D-MTPW-05); fragment-page hits feed the existing RenderPlan; collection hits feed the new templates.

Benefit: AC1/AC2 - pages from different tenants appear under their slugs on the same site.

Files: app/lib/resolver/page.ts, app/app/(website)/[[...slug]]/page.tsx

T-12 Tenant-prefixed fallback paths Mandatory

Problem it solves: a slug collision would otherwise make the losing page unreachable (AC7).

How we will solve it: when a slug resolves to a source that loses to a higher-priority source, serve the losing page under a tenant-prefixed path (exact prefix per Q7 answer); render both without redirect loops.

Benefit: deterministic, documented collision behavior.

Files: app/lib/resolver/page.ts

T-13 Per-source TTL cache + disabled-source 404 Mandatory

Problem it solves: per-source performance (request §8) and instant removal of disabled sources (AC6).

How we will solve it: TTL from the registry entry (default 300 s), key = source id + query params; disabling a source purges its cache entries immediately so its slugs 404.

Benefit: AC6 and the cache requirement in one place.

17. Test plan - step by step

Preparation: fixture environment (GW_DEV_FIXTURES=1) with at least two mock tenant public APIs (applicationstore-like and cms-like) registered as sources; one extra mock tenant for AC3; admin session for the source UI; real tenant pair only for the final publish gate.

17.1 Scenarios

  1. AC1 - applicationstore page appears. Steps: publish an object in the applicationstore-like fixture source, request its slug on www host. PASS if: page renders with the fragment body inside the shell within the cache TTL, with no deployment.
  2. AC2 - cms page appears alongside. Steps: publish an object in the cms-like source, request its slug. PASS if: both tenants serve pages on the same site at the same time.
  3. AC3 - third tenant onboarding. Steps: add one registry entry + one service token for the third mock tenant. PASS if: its pages serve with no code change.
  4. AC4 - private-object denial. Steps: request an om_private_objects id via /objects, /objects/{id}, every projection and fallback, on every fixture tenant. PASS if: always 404.
  5. AC5 - token isolation. Steps: use the applicationstore tenant token against another tenant and against content outside its key definition. PASS if: denied (401/403), and requests are logged per token.
  6. AC6 - disable removes pages. Steps: disable a source in the registry, request one of its slugs. PASS if: immediate 404 (no redeploy, cache purged).
  7. AC7 - slug collision. Steps: publish the same slug in two sources. PASS if: registry-order winner serves at the plain slug and the loser serves at its tenant-prefixed fallback path.
  8. AC8 - collection rendering. Steps: fixture collection source with products-like objects. PASS if: listing paginates, category groups by folder, detail lays out mapped fields, unpublished objects 404.
  9. AC9 - publish webhook (if built). Steps: publish an object then POST /hooks/publish with its id. PASS if: the page appears immediately (cache invalidated).

R-01 Private objects leaking through the public read API

Applies to: group PUBLIC-READ-API (T-05..T-09)

What can go wrong: a listing, detail read, fallback or projection path reads om_private_objects - raw tool code, chat sessions, snapshots and internal records become publicly reachable (production data breach).

Likelihood / impact: low with the single-path design / critical - this is the feature's absolute security rule (D-MTPW-03).

Mitigation: one allowlisted read path serving om_objects only; T-09 tests assert 404 for private ids in every endpoint, projection and fallback; token scope as second layer (D-MTPW-04).

Last re-evaluation: 2026-09-24 initial (plan stage) - kept critical: genuine production security rule; mitigation planned in T-09.

R-02 Service token leaks beyond its tenant

Applies to: group PUBLIC-READ-API (T-07, T-09)

What can go wrong: a token created for one tenant is accepted by another tenant, or reads content outside its key definition - unregistered content becomes readable (AC5 violated).

Likelihood / impact: medium if token scope is implemented loosely / high - unintended data exposure.

Mitigation: token → tenant binding enforced server-side per request (D-MTPW-09); viewer scope only (never write); scope and expiry follow the target tenant's CMS API key definition; negative tests in T-09; per-token request logging (T-08).

Last re-evaluation: 2026-09-24 initial (plan stage) - kept high; resolved only when T-09 passes.

R-03 Slug collisions misroute traffic to the wrong source

Applies to: group AGGREGATION-ROUTING (T-11, T-12)

What can go wrong: a page silently shows content from the wrong tenant when two sources share a slug; visitors are misled, links break.

Likelihood / impact: medium once many tenants serve the site / medium - wrong content under a real URL.

Mitigation: deterministic registry order (D-MTPW-05), tenant-prefixed fallback path for the loser, collision tests in T-14 and test scenario AC7.

Last re-evaluation: 2026-09-24 initial (plan stage) - medium.

R-04 Source outage or bad registry config breaks served pages

Applies to: groups SOURCE-REGISTRY and AGGREGATION-ROUTING (T-02, T-10, T-13)

What can go wrong: a tenant API down, a token expired or wrong folderIds make pages fail or disappear; with many sources this affects many URLs at once.

Likelihood / impact: medium / medium-high for the affected slugs.

Mitigation: per-source TTL cache serving within TTL (D-MTPW-08), deterministic error page + health fields, test connection button in the UI (T-03) so config is verified before enabling.

Last re-evaluation: 2026-09-24 initial (plan stage) - medium.

R-05 Malformed fragments break the site shell

Applies to: group AGGREGATION-ROUTING (T-10, T-11)

What can go wrong: a source object's body has html/head/body tags or global css; injecting it into the shell breaks layout, metadata or scripts for the whole page.

Likelihood / impact: medium once external tenants author fragments / medium - visual breakage, not data loss.

Mitigation: enforce the fragment contract (one root div, scoped css, idempotent js, no document tags - D-MTPW-06): validate or sanitize before mount; deterministic failure outcome in the matrix (section 9).

Last re-evaluation: 2026-09-24 initial (plan stage) - medium.

R-06 Registry changes take effect while misconfigured

Applies to: group SOURCE-REGISTRY (T-02, T-03)

What can go wrong: an admin edits an entry and pages vanish or degrade before anyone notices; no redeploy means no release rollback either.

Likelihood / impact: medium / low-medium for the affected slugs only.

Mitigation: test connection before enabling (T-03), per-source health (last success, error), schema validation (T-01), audit idea I-03.

Last re-evaluation: 2026-09-24 initial (plan stage) - low.

Overall verdict. Safe to start implementation locally. NOT safe to publish anything until groups SOURCE-REGISTRY, PUBLIC-READ-API and AGGREGATION-ROUTING are complete and the security tests (T-09) pass - the publish gate in section 17.2 is the only condition under which this feature may go public.
