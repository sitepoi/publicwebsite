# ADR-008 — Declarative flow engine + draft-state storage (C8 / M14)

Status: Accepted
Date: 2026-08-15

Context:
Section 31 turns purchasing/booking/ticketing/registration into data:
steps → fields → validations → payment → hooks, with server-side draft
state. C8 builds the flow engine on top of the C7 operations engine (hard
rule: operations are the ONLY set path for writes) and the Section 6B
DataProvider contract.

Decision:
- One route, `POST /api/flow/[flowId]`, dispatching on a strict
  `action: 'start' | 'step' | 'complete'` body (the plan sketches three
  sub-paths; a single route with a discriminated-union schema keeps one
  handler and the same semantics — flows stay data-driven).
- Flow definitions are objects in the website app (`data.flowId`, tolerant
  FlowDefinitionSchema). Steps carry `dataDefinitions`, `validationRules`,
  `paymentProvider` + `amountFormula`, and `hooks`.
- Validation subset (zod-ish, implemented by the engine, not raw zod):
  required, email, min, max, minLength, maxLength, regex, integer, with
  dotted field paths. Unknown rules fail loudly (no silent pass).
- Draft state (the documented storage choice): records in a DEDICATED
  collection `flow-states${tableExtension}` — the suffix follows the
  Section 6 / C6 convention `${name}${extension}` (form results), keeping
  admin-compatible naming. The client holds only the opaque flowStateId in
  an httpOnly `gw-flow-<sessionKey>` cookie (sessionKey = flow's `session`
  field, else the flowId); start sets the cookie, complete clears it.
- Reading draft state back required a DataProvider addition: `getRecord`
  (collection-scoped, symmetric with createRecord/updateRecord/
  deleteRecord). Firestore adapter implements it; the fixture adapter
  returns null (read-only dev double).
- Steps progress via `stepIndex`/`currentStep`; values accumulate in
  `state.steps[stepId]`. Complete requires the current step to be the LAST
  step and runs the done-step hooks:
  - `{ type: 'operation', operationId, payload? }` → executeOperation with
    templates resolved over `steps.*` / `user.*` and a per-state idempotency
    key `flow-<stateId>-<operationId>` (Section 33 — retries replay the same
    result instead of double-charging); a failed operation fails complete
    (502) and leaves the state in-progress.
  - `email` / `contextFunction` → existing hook runners, never fatal.
- Payment: a step with `paymentProvider` + `amountFormula` produces a Stripe
  intent STUB at complete: `{ provider, amount, currency, status:
  'requires_payment_method', id: 'pi_stub_…', stub: true }` — amount via the
  C7 formula evaluator over `state.steps` (Section 31:
  `cart.total + delivery.fee`). Real Stripe integration lands in C10.
- Guards mirror the data API: traffic rules, hashed-IP rate limit
  (60/60s, `flow:` prefix), honeypot `gw_hp` silent, optional per-folder
  reCAPTCHA for anonymous completes. Duplicate completes → 409
  flow-finished (single-shot per state).

Consequences:
- New verticals need only new flow configs — zero server code.
- Trade-off: the flow-state cookie is a single active flow per session key;
  parallel flows of the same key overwrite each other. Body-provided
  flowStateId remains the fallback for non-cookie clients. Multi-flow
  cookie maps can be added later without contract changes.
- Flow-state records are not yet visible in the admin UI (C12/M16 scope);
  the collection name is admin-compatible for when they are.
- Anon tokens are unauthenticated (opaque UUID); user-session binding
  arrives with auth sessions (C9).
