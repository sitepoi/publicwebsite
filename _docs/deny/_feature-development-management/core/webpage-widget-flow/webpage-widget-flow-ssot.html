1. Purpose and governance

The flow touches three systems and three codebases, and today no single document describes it end to end:

  1. CMS webpage builder (cms.uniconhub.com) - authors webpages and embeds website-html-tools as widget islands.
  2. Application store (applicationstore.uniconhub.com) - hosts the published website-html-tool catalog.
  3. publicwebsite renderer (www.uniconhub.com) - fetches pages from the CMS, renders them, discovers widget islands, fetches the tool code from the store and embeds it in the generated page.

Each project owns its section here and fills it in the same change as any code that alters its side of the contract. The renderer-side sections were verified from the publicwebsite code on 2026-10-09. The CMS builder side (this document's 8.1, 8.2, 8.4 write view, 8.7 authoring side, the CMS publish facts in 8.3 and D-WFLOW-09..13) was verified from the sitepoicms code on 2026-10-09. The WebpageBuilder TOOL side (the 8.1/8.2 tool-internals blocks, the tool rows of sections 2/3/9, the 8.4 note and D-WFLOW-14..16) was verified from the HTMLBasedTools repo code (app/WebpageBuilder.js build 2026-10-09-3) on 2026-10-09. The application store DEPLOYMENT internals (ssrHtml generation, versioning, SHELL markers, the revalidate webhook) remain explicit TO FILL blocks with questions, owned by the store deployment.

5. Verified problem and root cause

The knowledge of how a webpage with widgets travels from the CMS builder through the application store to www.uniconhub.com is scattered across three codebases. Each side knows its own half; the shared contract (field names, island markup, catalog endpoints, ssr markers, invalidation) has no single home.

Evidence: the publicwebsite AGENTS.md sync table already lists a page-rendering SSOT document that does not exist in the workspace; the builder-side and store-side behavior exists only as assumptions inside the renderer code (tolerated field aliases, envelope shapes, marker semantics).

Root cause: the three systems were built against each other's outputs without one shared design document, so the contract drifted (example: pages store webpageContentWithBuilder.code while the renderer's fixed field is htmlPage.code - the renderer reads both as aliases).

6. Requirements

  1. R-01 - the CMS webpage builder creates pages and saves their content and widget islands (section 8.1/8.2).
  2. R-02 - published website-html-tools become catalog records in the application store (section 8.3).
  3. R-03 - the builder lists tools from the store, selects one, adds it to the page at a chosen location and previews it (section 8.2).
  4. R-04 - the storage layout of page content, widget references and tool code is documented in one place (section 8.4).
  5. R-05 - the publicwebsite renderer fetches pages from the CMS data layer and matches URLs/slugs to objects with folder-based multi-site isolation (section 8.5).
  6. R-06 - the renderer discovers islands inside page content, fetches the tool code from the store server-side, embeds SSR markup and hydrates the tool on the client (section 8.6).
  7. R-07 - a widget can be configured to read its content from another CMS application's data, with access control (section 8.7).
  8. R-08 - republishing a tool in the store reaches the website without republishing every page (invalidation chain, section 8.6).
  9. R-09 - every project can read this document and understand how the other parts work.
  10. R-10 - verified facts and explicit open questions are recorded separately, never mixed.

Why ssrHtml exists, and the Q-07 decision (ANSWERED 2026-10-09, option (e) - see D-WFLOW-19): most widgets are TOOLS (forms, calculators) and are not content for bots to index, so the default stays template mode (code.html as the SSR markup) and NO separately saved ssrHtml is produced. ssrHtml earns its place only for CONTENT widgets (e.g. an education widget) where SEO and first-paint speed matter. Content widgets need page-related data, which neither the applicationstore (holds code only) nor the tool builder (one step behind the store) can supply - the data comes from the page the widget is called on. Two generation sites are therefore supported, chosen per page/widget in the WebpageBuilder and saved into the page config: (1) builder-static (Gatsby-like SSG) - the builder merges page data + widget code and bakes a static ssrHtml; it must re-run whenever the data changes (e.g. a restaurant menu) - wiring that trigger is the Q-10 revalidate webhook. (2) publisher-dynamic (Next.js-like SSR) - the renderer merges the widget with its page data at request time and caches the result (L1 memory, L2 Redis, CDN - not built yet); more dynamic, more costly. For static/tool widgets the page config simply stays on the default template mode.

SUPERSEDED 2026-10-10 (Q-36/D-WFLOW-30): the store record carries no ssrHtml and no companion-document reference - per-page widget data is written page-side by the builder and combined with the tool by the renderer when the page renders. The paragraph below is kept as history.

ssrHtml STORAGE (decided 2026-10-10, D-WFLOW-21 - historical, SUPERSEDED by D-WFLOW-30): when ssrHtml is enabled, each generated snapshot is stored in ANOTHER Firestore document (its own doc - never inside the widget code record, which can grow too large and must stay under the 1 MB Firestore document limit). Tool-style islands (SSR modes 1/template/client, no factory) mount silently with data-gw-mounted="1". configSchema defaults fill missing config keys. Widget css is appended AFTER page css (style[data-gw-widget-css], deduped per name). Widget shells (ssr markup) are re-injected after every mount rebuild so tool code finds its markup on SPA re-init.

I-02 Content-Security-Policy for the public website

Idea: add a Content-Security-Policy to the public website, introduced in two phases so it can never break the platform: phase 1 = the safe subset, phase 2 = script/style/frame/connect (L-03, Q-20).

Why: the site runs code that did not come from this repo (store widgets) and injects markup/styles at runtime, so CSP is the last line of defence - it can stop a bad or compromised widget from talking to unknown hosts, block injected remote scripts, prevent clickjacking, and close the cheap tricks (base-uri, object-src, form-action).

PHASE 1 - the subset that cannot break anything (enforce this one day): frame-ancestors 'self' + any UniconHub host that must frame a site (same-ORIGIN only, not same-company); object-src 'none' (kills <object>/<embed> only - iframes unaffected); base-uri 'none' (no <base> exists in the renderer today); form-action 'self' - trial it in Report-Only first, it is the only phase-1 directive that can bite (a native form posting to a foreign host, or a same-origin submit that redirects off-origin, e.g. an external payment page); upgrade-insecure-requests optional (only hits old http:// assets/embeds).

PHASE 2 - deliberately deferred, needs a nonce/hash strategy, not just allowlists: script-src must keep working for blob: widget code (code.js runs from a Blob URL), for the inline gw bootstrap, and for the EXTERNAL scripts the platform itself emits - gtag + GTM (www.googletagmanager.com), ShareThis (platform-api.sharethis.com), the Meta pixel - plus vendored same-origin DOMPurify (/vendor/purify.min.js) and /gw-widgets.js. style-src must allow runtime-injected <style> tags (page css, widget css, sharedCss). connect-src must allow the data API, the appstore proxy and the SSE subscribe stream (tools that call a third-party API directly would need their host listed). frame-src must allow the intended embeds (YouTube, maps, calendars).

Facts to remember: iframes (including iframe-in-iframe) are NEVER restricted by phase 1 - a child frame is judged by its own policy, not ours; frame-ancestors cannot be trialled in Report-Only because nothing loads and therefore nothing can be reported - it has to be enforced deliberately; content merged server-side from the CMS (html/css/js) and blob-URL widget code are unaffected by phase 1.

Pre-flight before enforcing: (1) does any UniconHub host frame a public site, and which one? (2) does any page post a native form to a host other than its own? (3) any <object>/<embed> usage? (4) any http:// assets.

Outcome (2026-10-10): DEFERRED on purpose - do not apply now, keep the plan and re-open when asked (Q-20 answered (c), D-WFLOW-26).
